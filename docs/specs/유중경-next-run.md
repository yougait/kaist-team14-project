# 다음 러닝 코칭 카드 기능 명세

- 작성자: 유중경 / KAIST 14조 KNEECH
- 작성일: 2026-10-28
- 버전: 1.0 / 개인 과제용 합성 데이터 프로토타입
- 원안: KNEECH_Next_Run_Spec_v01.md, 2026-10-17

## 1. 누구의 어떤 문제를 다루는가

대상은 측정 결과를 읽었지만 다음 러닝에서 무엇을 해 볼지 정하기 어려운 성인 생활 러너다. 부스 설명을 들은 뒤 다음 러닝 직전에 계획을 확인하고, 러닝 종료 후 실행 여부를 남기는 순간을 다룬다. 이 사용자의 필요는 아직 고객 검증을 마친 사실이 아니라 제품 가설이다.

이번에 확인할 것은 ‘행동 한 가지를 선택하고 다시 찾아 실행 후 기록을 남길 수 있는가’다. 자세 교정 효과나 건강 개선을 검증하는 기능이 아니다.

## 2. WhyTree의 어느 노드를 위한 기능인가

`docs/whytree/유중경.md`의 두 번째 트리에서 아래 경로에 해당한다.

내 몸을 이해하며 달리기 지속 > 실행 가능한 선택 > 다음 러닝 코칭 카드

‘다음 러닝 코칭 카드’는 원본 슬라이드의 점선 연결처럼 ‘일상 속 실천 지속’에도 기여한다. 체크인은 같은 사용 흐름을 마무리하는 부분이다. ‘비교 가능한 후속 결과’ 전체 기능과 ‘코치의 후속 확인’ 운영 도구는 이번에 구현하지 않는다.

## 3. 사용자가 하는 일

1. ‘승인된 데모’ 등 내장 가상 자료를 선택하거나 같은 형식의 합성 JSON을 불러온다. 모든 화면과 출력에 ‘합성 데이터 데모’를 표시한다.
2. 자료의 과제 종류, 출처, 센서 방향, 측정값과 단위, 검토 상태를 읽는다. 없는 값은 ‘자료 없음’으로 표시한다.
3. 사전 승인 상태인 행동 한 가지를 확인하고 실행 날짜를 입력한다. 확인 체크와 유효한 날짜가 모두 있어야 계획을 저장한다.
4. 같은 브라우저에서 새로고침하여 행동과 날짜가 복원되는지 확인한다.
5. 실행 후 ‘실행함 / 일부 실행 / 실행하지 않음’ 중 하나를 선택하고 어려움과 새로운 불편 여부를 기록한다. 과제용 데모에서는 가상으로 실행 후 상황을 입력할 수 있다.
6. 지난 기록에서 계획과 실제 실행 기록을 함께 확인한다. 자가보고를 측정값이나 효과로 바꾸지 않는다.
7. 새 불편이 있으면 ‘담당자 검토 필요’로 바꾸고 다음 자동 진행을 차단한다. 미승인 자료에서는 계획을 만들 수 없다.

## 4. 우선순위와 완료 조건

| 우선순위 | 항목 | 완료 조건 |
|---|---|---|
| P0 | 합성 자료 불러오기 | 내장 정상·미승인·단측 누락·과제 불일치 자료와 합성 JSON 입력을 지원한다. 형식이 틀리거나 실제 자료 모드이면 기존 상태를 덮어쓰지 않고 거절한다. |
| P0 | 사실 표시 | source, movement_type, sensor_sides, metric.value/unit, review_status를 표시한다. null은 0으로 만들지 않는다. 단측 자료에서 좌우 비대칭을 만들지 않는다. |
| P0 | 행동과 날짜 저장 | 승인된 행동 하나만 표시한다. 사용자 확인과 올바른 날짜를 요구한다. 같은 카드에서 중복 계획을 만들지 않는다. |
| P0 | 체크인과 지난 기록 | 실행 상태·어려움·새 불편을 계획에 연결해 저장한다. 같은 카드의 체크인을 두 번 추가하지 않는다. 새 계획은 새 데모 자료를 불러와 시작한다. |
| P0 | 예외 처리 | 승인 없음·새 불편이면 검토 필요를 표시한다. 비교 자료 없음·과제 다름·지표 누락이면 비교 보류 사유를 표시한다. 수치 개선률과 좋음/나쁨 점수는 만들지 않는다. |
| P0 | 복원과 초기화 | 브라우저 저장소에서 복원하고, 초기화는 확인 후 이 프로토타입의 기록만 지운다. 저장 실패·손상된 저장 자료를 명시하며 저장했다고 잘못 알리지 않는다. |
| P0 | 화면과 출력 일치 | 인쇄 기능은 현재 화면의 같은 기록을 출력한다. 합성 자료 표시와 예외 사유를 유지한다. 외부 서비스 호출과 추적 스크립트는 없다. |
| P1 | 생성 AI 설명 | 검토된 사실과 승인 행동의 표현을 쉽게 바꾼다. 모델·데이터 조건 확정 전까지 비활성이다. |
| P1 | 실제 센서 파일 연동·알림 | 실제 파일 규격 확인, 사용자 동의와 전달 실패 처리가 필요하므로 후순위다. |
| P1 | 인증·서버 저장·담당자 검토 화면 | 실제 참가자 운영 전 필요한 별도 개발이다. 합성 자료 개인 과제 범위에는 포함하지 않는다. |
| P2 | 다회차 측정 비교·BLE·개인화 | 비교 기준과 제품 사용성 근거를 확보한 뒤 다룬다. |

## 5. 범위 밖

실제 사람의 건강 기록·연락처 입력, 진단이나 운동 처방, 통증 점수에 따른 안전 판정, 신규 교정 행동 생성, 운동 강도 자동 변경, 임상적 효과 판정, 외부 메시지 발송, 다른 기기 동기화, 회원 가입, 결제, 전체 니치 앱 구현은 제외한다.

‘승인됨’은 합성 자료 안의 가상 상태다. 실제 전문가가 행동을 승인했다거나 제품의 성능이 검증됐다는 뜻이 아니다. 사용 가능한 예시 행동도 특정 자세나 운동 용량을 처방하지 않는 기록 행동으로 제한한다.

## 6. AI 모델과 실패 시 처리

P0 실행 중 사용하는 생성 AI 모델은 **없음**이다. 브라우저에서 정해진 문구와 규칙을 사용하므로 API 키가 필요 없다. 개발을 돕는 코딩 에이전트와 제품 안에서 동작하는 AI를 구분한다.

P1의 모델 식별자는 아직 정하지 않았다. 향후 모델을 넣더라도 시간 초과, 형식 오류, 미승인 행동 ID, 없는 숫자·출처를 포함한 응답은 폐기하고 현재의 고정 문구로 돌아온다. 모델은 승인 여부나 상태 전이를 결정하지 않는다.

## 7. 입력과 상태

입력 JSON은 `schema_version: 1`, `mode: "synthetic"`, session_id, movement_type, source, sensor_sides, metric, review_status, action, optional followup으로 구성한다. source는 synthetic이어야 한다. metric은 label·value(유한한 숫자 또는 null)·unit·side를 가진다. action은 id와 text를 가진다. movement_type은 run 또는 walk_figure8, review_status는 approved 또는 pending, sensor_sides는 left/right의 비어 있지 않은 배열이다. 임의의 실제 식별정보 필드는 저장하지 않으며 표시 문자열은 HTML로 실행하지 않는다.

기본 상태는 `ready → planned → checked_in`이다. 미승인 자료 또는 새 불편은 `review_required`로 처리한다. 상태와 별도로 `comparison_note`에 비교 보류 이유를 보여 준다. P0에서는 같은 과제여도 비교 기준 검토 전이므로 수치 효과를 계산하지 않는다.

저장은 해당 브라우저의 localStorage 한 키로 제한한다. 서버 전송·암호화·다른 기기 백업을 제공하지 않는다. 과제용 합성 자료만 사용한다. 기록 변경·계획·체크인 이벤트는 같은 저장 자료 안에 중복 없이 남긴다.

날짜는 실제 달력에 있는 YYYY-MM-DD 형식이어야 한다. 계획은 저장하는 시점의 기기 현지 날짜보다 이전일 수 없다. 저장 후 다음 날에 읽는 기존 계획은 과거 날짜가 되어도 보존한다.

## 8. 손으로 확인하는 세 가지 검사

### T1 정상 흐름과 저장 복원

1. 초기화 후 ‘승인된 데모’를 선택한다. 행동 확인을 하지 않거나 날짜를 비우면 계획 저장이 되지 않는지 확인한다.
2. 행동을 확인하고 오늘 또는 미래 날짜로 저장한다. 저장을 두 번 눌러도 계획이 하나인지 확인한다.
3. 새로고침 후 행동과 날짜가 같은지 확인한다. ‘일부 실행’과 어려움, ‘새 불편 없음’을 저장하고 다시 새로고침한다.
4. 지난 기록에 계획·실행 상태·어려움이 남고 체크인이 하나인지 확인한다. 인쇄 미리보기에도 같은 내용과 데모 표시가 있는지 확인한다.

통과: 선택한 행동·날짜·체크인이 정확히 복원되고 중복 기록이 없다.

### T2 진행 차단과 자료 해석

1. ‘미승인 데모’를 선택한다. 새 계획 저장이 차단되고 담당자 검토 필요가 표시되는지 확인한다.
2. ‘승인된 데모’로 계획을 만든 뒤 새 불편을 ‘있음’으로 저장한다. 검토 필요 상태가 유지되고 다음 자동 진행이 없는지 확인한다.
3. ‘단측·누락 데모’에서 자료 없음과 단측 표시를 확인한다. 0이나 좌우 균형 점수가 나오면 실패다.
4. ‘과제 불일치 데모’에서 ‘비교 보류: 과제 다름’을 확인한다. 러닝 개선률이 나오면 실패다.

통과: 데이터의 한계와 검토 필요 사유를 그대로 표시하며 새 교정·효과를 만들지 않는다.

### T3 잘못된 입력과 초기화

1. 제공된 예시 JSON을 불러와 정상 표시를 확인한 뒤, mode를 real로 바꾸거나 잘못된 JSON을 입력한다. 오류를 표시하고 기존 기록은 보존해야 한다.
2. 브라우저 저장이 막힌 환경에서는 저장 실패 또는 임시 상태라는 안내가 나와야 한다. 저장 완료로 표시하면 실패다.
3. 초기화 확인창에서 취소하면 기록이 남고, 승인하면 이 앱 기록만 삭제되는지 확인한다. 다시 열었을 때 새 데모 시작 화면인지 확인한다.

통과: 입력·저장 오류가 조용히 숨겨지지 않고 잘못된 자료로 기존 기록을 덮어쓰지 않는다.

검사 기록은 `prototypes/유중경/TEST_RESULTS.md`에 검사자·방법·실제 결과를 적는다. 에이전트의 검사는 본인의 손 검사와 별도로 기록한다.

## 9. 설계 결정과 변경 이력

### D1 2026-10-28 범위 확정

질문: 가상 자료, 승인된 행동 한 가지, 날짜 저장, 실행 후 체크인, 기록 재조회를 P0로 완성하고 생성 AI·센서 연동·알림을 후순위로 둘 것인가?

유중경 답변: ‘네, 이 범위로 완성해 주세요 (추천)’.

이에 따라 원안의 큰 서비스 설계를 개인 과제용 한 흐름으로 좁혔다. 실제 참가자 보호조치와 인증은 실제 운영 전에 필요하지만, 이 프로토타입에서는 실제 참가자 자료를 입력하지 않는다.

### D2 구현 중 변경

기능 요구사항 변경은 없었다. P0는 위 명세대로 구현했다. 첫 화면 검토에서 모바일·인쇄 제목의 단어 사이 공백이 사라지는 표시 문제를 고쳤으며, 이는 기능 범위나 상태 규칙의 변경이 아니다. 검사 결과는 `prototypes/유중경/TEST_RESULTS.md`에 기록했다. 이후 조건을 바꿀 필요가 생기면 이 절과 관련 요구사항을 먼저 바꾸고 코드를 수정한다. 본인이 검사를 하지 않았거나 실패가 없었다면 회고에 실패 사례를 만들어 넣지 않는다.
